# Дневник разработки — SMR-Pro Search

Хронологическое описание реализации и проблем, возникших в ходе работы.
Составлено по истории сессии с Claude Code.

---

## 1. Запуск проекта

### Проблема: `make run` не работает на Windows
`make run` вызывал `bash scripts/run_all.sh`, но `bash` не был доступен в PATH.
Команда `make` была установлена через Chocolatey.

**Решение:** Заменён `bash`-скрипт на кроссплатформенный Python-эквивалент
`scripts/run_all.py`. Он запускает сервисы через `subprocess.Popen`, а для
остановки использует `taskkill /PID /F` вместо `kill`. Цели `run` и `stop`
в `Makefile` переписаны на `$(PY) scripts/run_all.py`. Также переписан
`clean` — убраны `rm -rf` и `find`, заменены на Python-однострочники через
`shutil` и `pathlib`.

## 2. Первый запуск — краш UI

### Проблема: `TypeError: 'builtin_function_or_method' object is not iterable`
При поиске `/search` возвращал HTTP 500. Шаблон `results.html` содержал
`{% for item in result.items %}` — Jinja2 разрешает `result.items` через
`getattr`, находит встроенный метод `dict.items` и возвращает его объект,
а не значение по ключу `"items"`.

**Решение:** Заменено на `result['items']` (квадратные скобки форсируют
`__getitem__` и обходят `getattr`). Та же проблема устранена превентивно
во всех шаблонных обращениях к словарным ключам с именами, совпадающими
с методами dict.

## 3. Панель отладки пайплайна в UI

Добавлена кнопка-тоггл «Как работал поиск» на странице результатов.
При нажатии раскрывается панель из 4 карточек — по одной на каждый
микросервис пайплайна.

**Что показывает каждая карточка:**
- **Предобработка**: оригинал → исправленный запрос, леммы, расширение, тип
- **Поиск**: кол-во кандидатов, топ-5 с BM25/SBERT/RRF-скорами
- **Ранжирование**: топ-5 с итоговым score и значениями признаков
- **Постобработка**: кол-во итоговых позиций и комплектов

**Реализация:** Поле `debug: Dict[str, Any]` добавлено в `SearchResponse`
(модель Pydantic). Gateway-pipeline заполняет его данными промежуточных
шагов. Шаблон использует `result['debug']['preprocess']` и т.д.

## 4. Gateway падает при запросе — сервис retrieval не готов

### Проблема: `ConnectionRefusedError` на `localhost:5002`
Сервис retrieval загружает SBERT-модель (~5 секунд), а gateway уже
принимает запросы. Первый запрос сразу после `make run` падал с ошибкой.

**Решение:** В `gateway/pipeline.py` в функцию `_post()` добавлена логика
повтора: 3 попытки с задержками 1, 2, 4 секунды при `ConnectionError`.
`HTTPError` (сервис жив, но вернул 5xx) не повторяется.

---

## 5. Поиск возвращает 0 результатов

### Диагностика по логам
Логи показали: `ranking: rank: 0 candidates` при каждом запросе. Причина —
retrieval отправляет 0 кандидатов, потому что:
- `BM25 index not found – run training`
- `FAISS index/id-map missing – run training`

### Причина: обучение было прервано
В `data/indices/` были только `.gitkeep`-файлы. В `data/models/` была
FastText-модель, но не было BM25-индекса, FAISS-индекса и словаря SymSpell.
Это означало, что обучение дошло до шага 4 (FastText) и было прервано —
вероятно, потому что шаг 6 (FAISS) требует энкодинга 252 000 расценок
с SBERT, что на CPU занимает часы.

**Решение:** В `training/build_indices.py` добавлен флаг `--skip-faiss`.
Добавлена цель `make train-bm25` — запускает пайплайн без SBERT и FAISS.
BM25-индекс строится за несколько минут и обеспечивает базовый поиск.

## 8. Несоответствие баз нормативов 2012 и 2022 года

### Проблема
Исторические XML-сметы использовали базу 2012 года (`baza="2012"`).
Каталог SMR-Pro (`smr_catalog.db`) использует базу 2022 года.
Коды материалов изменились: например, `М101-25300` (2012) → `1/10-10-5/5` (2022).

**Последствия:** Транзакции в БД хранили старые коды → FP-Growth строил
правила по старым кодам → `kit_builder` искал правила по новым кодам →
технологические комплекты не находились никогда.

### Решение
Добавлен файл `data/raw/materialCodesDictionary.csv` (190 695 строк,
183 764 маппинга с непустым KOD22).

**`common/code_mapper.py`** — синглтон, загружает CSV один раз, предоставляет
`translate(code)` и `translate_list(codes)`.

**`training/ingest_xml.py`** — при новых ingestion-ах автоматически переводит
коды перед записью в БД.

**`scripts/migrate_code_mapping.py`** — применена к существующим данным:
- Проверено: 54 346 транзакций
- Обновлено: 16 578 транзакций
- Замен кодов: 44 171

## 9. PTM-справочник и расширение системы

Добавлен файл `data/raw/ptms.csv` — 596 предустановленных ПТМ с канонными
наименованиями. Поле `PRM` содержит 5 частей через `#`:
`код # уровень # наименование # описание # пусто`.

Использован в трёх местах:

### 9а. FastText corpus (train_fasttext.py)
Добавлены названия и описания из CSV в обучающий корпус FastText.
Также дедуплицированы `ptm_naim` из транзакций (раньше одно имя
добавлялось N раз). Более богатый корпус улучшает качество query expansion.

### 9б. PTM-retrieval (новый путь поиска)
**`training/build_ptm_index.py`** — строит индекс из 12 671 ПТМ-записи
(596 из CSV + 12 075 пользовательских из транзакций). Структура:
- `ptm_list`: записи с токенами и топ-50 расценок по частоте
- `token_to_ptms`: инвертированный индекс токен → [индексы ПТМ]

**`services/retrieval/ptm_search.py`** — при запросе находит ПТМ с
совпадающими токенами, агрегирует их расценки взвешенно по
`ptm_overlap_score × rascenka_freq`, возвращает до 100 кандидатов.

**`services/retrieval/rrf_fusion.py`** — расширен до трёх источников:
BM25, SBERT, PTM. Результат каждого потока получает RRF-вклад через
`1 / (k + rank)`.

**`common/models.py`** — в `CandidateScore` добавлены поля `ptm_score`
и `ptm_rank`. В `feature_extractor.py` добавлен признак `f12_ptm`.
Веса линейного fallback-ранкера скорректированы (PTM получил 10%).

### 9в. Классификатор типа запроса (train_query_classifier.py)
Заменён хардкод `AGGREGATED_CONCEPTS` (9 фраз) на ML-классификатор.

**Данные:**
- Aggregated: 596 имён из CSV + субфразы (2-4 слова) из длинных PTM-имён
  + 15 484 отфильтрованных PTM-имён из транзакций — итого ~16 700
- Atomic: 20 000 первых 4 слов из имён расценок каталога

**Модель:** TF-IDF (char_wb n-grams 2-4, 50k признаков) + LogisticRegression
с `class_weight='balanced'`. Обучение ~4 секунды.

**Результат:** 97.5% accuracy на held-out тестовой выборке.

**Порог:** снижен с 0.5 до 0.42 (через `predict_proba`) — делает модель
чуть чувствительнее к агрегированным запросам, так как пропустить
технологический комплект хуже, чем предложить лишний.

## Описание системы

### Назначение

SMR-Pro Search — интеллектуальная поисковая система по нормативной базе
сметного программного обеспечения SMR-Pro. Пользователь вводит текстовый
запрос на естественном языке («монтаж системы отопления», «тёплый пол»,
«ЕР46-01-008»), система возвращает ранжированный список расценок и,
для агрегированных запросов, предлагает технологические комплекты —
наборы расценок, которые исторически использовались вместе.

### Источники данных

| Файл | Содержимое | Размер |
|---|---|---|
| `data/raw/smr_catalog.db` | Нормативная база SMR-Pro 2022 г. (расценки, материалы, механизмы, оборудование, группы расценок) | ~1.2 ГБ |
| `data/raw/xmls/*.xml` | Исторические сметы в формате XML (177 файлов, 54 346 ПТМ) | ~200 МБ |
| `data/raw/materialCodesDictionary.csv` | Словарь перевода кодов 2012→2022 (190 695 строк) | ~34 МБ |
| `data/raw/ptms.csv` | Справочник 596 предустановленных ПТМ с канонными наименованиями | ~53 КБ |

После обработки всё сводится в одну рабочую БД `data/smr_pro.db` (SQLite):

| Таблица | Строк | Назначение |
|---|---|---|
| `rascenka` | ~252 000 | Каталог нормативных позиций |
| `rate_groups` | ~12 000 | Иерархия групп расценок |
| `transactions` | ~54 000 | ПТМ из исторических смет |
| `rascenka_profile` | ~34 000 | Частотные профили расценок |
| `association_rules` | — | Правила FP-Growth |
| `user_feedback` | — | Клики пользователей (для CatBoost) |

### Архитектура: микросервисный пайплайн

Система состоит из 6 Flask-процессов, запускаемых одновременно. Каждый
запрос пользователя проходит через 4 сервиса последовательно:

```
Браузер
   │  GET /  (поисковая страница)
   │  POST /search  (отправка запроса)
   ▼
┌─────────────────────────────────┐
│  UI  :8080  (ui/app.py)         │
│  Flask, Jinja2-шаблоны          │
│  Кнопка «Как работал поиск»     │
└────────────┬────────────────────┘
             │ POST /search  {query, context}
             ▼
┌─────────────────────────────────┐
│  Gateway  :5000                 │
│  (services/gateway/)            │
│  Оркестрирует пайплайн,         │
│  замеряет время каждого шага,   │
│  retry при ConnectionError      │
└──┬──────┬──────┬──────┬─────────┘
   │      │      │      │
   ▼      ▼      ▼      ▼  (последовательно)
  [1]    [2]    [3]    [4]
```

#### [1] Preprocessing  `:5001`  `services/preprocessing/`

Принимает сырой текст запроса, возвращает нормализованное представление.

**Spell correction — `spell_correction.py`**
Использует SymSpell (словарь построен из имён расценок и групп, ~50к токенов).
При отсутствии словаря пропускается без ошибки.

**Lemmatization — `lemmatizer.py`**
pymorphy2: приводит каждый токен к нормальной форме.
`«монтажа» → «монтаж»`, `«отопительных» → «отопительный»`.

**Query expansion — `query_expander.py`**
Два источника объединяются:
- Курированный тезаурус (13 записей, например `«покраска» → [«окраска», «окрашивание»]`)
- FastText: top-3 ближайших соседа с cosine similarity ≥ 0.65

**Query type classification — `classifier.py`**
Определяет тип запроса:
- `atomic` — пользователь ищет одну конкретную расценку
- `aggregated` — пользователь ищет технологию/пакет работ

Приоритет решений:
1. Regex: код вида `ЕР46-01-008` или `А58-4-1` → всегда `atomic`
2. ML-модель: TF-IDF (char_wb ngrams 2-4) + LogisticRegression, порог 0.42
3. Fallback: ≤2 слова → `atomic`, >2 → `aggregated`

Ответ (`PreprocessResponse`):
```json
{
  "original": "монтаж системы отопления",
  "corrected": "монтаж системы отопления",
  "lemmas": ["монтаж", "система", "отопление"],
  "expanded_terms": ["установка", "монтировать", "тепло"],
  "query_type": "aggregated"
}
```

---

#### [2] Retrieval  `:5002`  `services/retrieval/`

Три независимых потока поиска кандидатов, результаты сливаются через RRF.

**BM25 — `bm25_search.py`**
Индекс построен на основе `rank_bm25.BM25Okapi`. Текст каждой расценки
дополнен путём к группе расценок («Малярные работы | Глава 15»), что
позволяет запросу «малярные работы» подтягивать все позиции этой группы.
Поиск ведётся по леммам + расширенным терминам. Возвращает до 100 кандидатов.

**SBERT + FAISS — `semantic_search.py`**
Модель `DeepPavlov/rubert-base-cased-sentence` (768-мерные эмбеддинги).
FAISS `IndexFlatIP` (точный поиск по inner product, т.е. cosine для
нормализованных векторов). Запрос кодируется в вектор, ищутся
ближайшие соседи среди 252к векторов расценок. При наличии GPU
используется автоматически (`SentenceTransformer(device='cuda')`).

**PTM-retrieval — `ptm_search.py`**
Новый путь поиска, основанный на исторических ПТМ. Индекс (12 671 запись)
строится из транзакций: для каждого ПТМ хранится топ-50 расценок по частоте
вхождения. При поиске:
1. Токены запроса сопоставляются с токенами наименований ПТМ (инвертированный индекс)
2. ПТМ ранжируются по доле совпавших токенов (overlap fraction)
3. Расценки из топ-5 ПТМ агрегируются с весом `ptm_overlap × rascenka_freq`

**RRF fusion — `rrf_fusion.py`**
Reciprocal Rank Fusion объединяет три потока:
`score(d) = Σ 1/(k + rank_i(d))`, где k=60 (константа, сглаживающая влияние
высоких позиций). Возвращает топ-100 кандидатов с раздельными скорами каждого
потока (`bm25_score`, `sbert_score`, `ptm_score`, `rrf_score`).

---

#### [3] Ranking  `:5003`  `services/ranking/`

Переранжирует кандидатов используя 12 признаков.

**Feature extractor — `feature_extractor.py`**

| Признак | Описание |
|---|---|
| f1 | BM25 raw score |
| f2 | SBERT cosine similarity |
| f3 | Доля токенов запроса, найденных в наименовании расценки |
| f4 | 1 / BM25 rank |
| f5 | 1 / SBERT rank |
| f6 | Нормированная абсолютная частота расценки в исторических сметах |
| f7 | Контекстуальная частота: как часто расценка встречается в ПТМ с тем же кодом |
| f8 | Актуальность (всегда 1.0, зарезервировано) |
| f9 | Хеш типа объекта из контекста |
| f10 | Хеш региона из контекста |
| f11 | Хеш главы сметы из контекста |
| f12 | PTM aggregated score |

**Ranker — `ranker.py`**
В норме: CatBoost (`CatBoostRegressor`, pointwise LTR, обучается на
`user_feedback`). При отсутствии обученной модели — линейная комбинация
признаков с ручными весами:
`0.28·f2 + 0.18·f4 + 0.18·f5 + 0.14·f1 + 0.10·f12 + 0.05·f3 + ...`

Возвращает топ-20 ранжированных позиций.

---

#### [4] Postprocessing  `:5004`  `services/postprocessing/`

Формирует технологические комплекты к результатам поиска.

**Kit builder — `kit_builder.py`**
Берёт топ-N расценок из результатов (N=5 для `atomic`, N=8 для `aggregated`).
Для каждой расценки-«зерна» запрашивает ассоциативные правила из БД
(FP-Growth, antecedent содержит код расценки). Consequent'ы правил
агрегируются, дедуплицируются и возвращаются как `TechKit`.

Правила FP-Growth построены с параметрами:
- min_support = 0.03 (расценки встречаются в 3%+ смет)
- min_confidence = 0.6
- min_lift = 1.0
- max_itemset_len = 8

### Обучающий пайплайн

`make train` запускает `training/pipeline.py` — 8 шагов:

```
[0/8] Импорт каталога из smr_catalog.db
        → ~252k расценок, ~12k групп
        → фильтрация кодов с * (20 136 пропущено)

[1/8] Ingestion XML-смет
        → 177 файлов, 54 346 ПТМ
        → трансляция кодов 2012→2022

[2/8] Статистические профили
        → f_abs, f_norm, ctx_json для каждой расценки

[3/8] FP-Growth
        → ассоциативные правила между расценками

[4/8] FastText
        → обучение на именах расценок + ПТМ-наименованиях из CSV и транзакций
        → используется для query expansion

[5/8] SBERT fine-tune
        → позитивные пары: (ptm_naim, rascenka_naim)
        → MultipleNegativesRankingLoss
        → GPU если доступен (batch 64 vs 16)

[6/8] Индексы
        → BM25 index (rank_bm25.BM25Okapi)
        → FAISS (GPU encoding, batch 256 vs 32)
        → SymSpell dictionary
        → PTM index (12 671 записей)

[7/8] Query classifier
        → ~36k примеров (16k aggregated + 20k atomic)
        → TF-IDF char ngrams + LogisticRegression

[8/8] CatBoost
        → только если есть user_feedback (min 20 строк)
        → GPU если доступен (task_type='GPU')
```

## Итоговая архитектура (схема)

```
Пользователь
    │
    ▼
UI (Flask, :8080)
    │ POST /search
    ▼
Gateway (:5000)
    │
    ├─[1] Preprocessing (:5001)
    │       spell correction (SymSpell)
    │       lemmatization (pymorphy2)
    │       query expansion (FastText)
    │       type classification (TF-IDF + LogReg, 97.5% acc)
    │
    ├─[2] Retrieval (:5002)
    │       BM25 (rank_bm25, ~252k расценок)
    │       SBERT + FAISS (DeepPavlov/rubert-base-cased-sentence)
    │       PTM-retrieval (12k PTM-записей, инвертированный индекс)
    │       RRF fusion (3 потока, k=60)
    │
    ├─[3] Ranking (:5003)
    │       12 признаков (f1-f12)
    │       CatBoost (GPU) или linear fallback
    │
    └─[4] Postprocessing (:5004)
            FP-Growth association rules (support≥0.03, conf≥0.6)
            kit_builder → технологические комплекты
```

**Файлы данных (после обучения):**
- `data/smr_pro.db` — SQLite: ~252k расценок, ~54k транзакций
- `data/indices/bm25_index.pkl` — ~113 МБ
- `data/indices/ptm_index.pkl` — ~10 МБ
- `data/indices/faiss.index` — ~740 МБ (при полном обучении)
- `data/models/fasttext.model` — ~840 МБ
- `data/models/symspell_dict.txt` — ~2 МБ
- `data/models/query_type_classifier.pkl` — ~5 МБ

## Команды запуска

```bash
# Полный цикл с нуля
make clean            # остановить сервисы и удалить все артефакты
make install          # установить зависимости
make train            # полное обучение (SBERT+FAISS требует GPU или ~5ч на CPU)
make train-bm25       # быстрое обучение без SBERT/FAISS (~10 мин)
make run              # запустить все сервисы → http://localhost:8080

# Обслуживание
make stop             # остановить сервисы
make migrate-codes    # перевести коды 2012→2022 в существующих транзакциях
make train-classifier # переобучить только классификатор типа запроса
```
